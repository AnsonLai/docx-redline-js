## @ansonlai/docx-redline-js v0.7.2

Version 0.7.2 is an agent-surface simplification release. It eliminates the
deliberation overhead, "choice tax", and speculative recovery loops observed in
AI-driven document editing under v0.7.0 and v0.7.1. By re-establishing a single,
deterministic two-turn "extract-then-apply" golden path as the default agent
workflow, v0.7.2 provides predictable execution while retaining the payload
token savings of localized replacements and all 0.7.x capabilities.

The engine remains OOXML-only and host-independent. This release adds no
runtime dependency and does not require Microsoft Word, Office automation, COM,
or a proprietary document API. Core mutation, reconciliation, package
validation, rollback, comments, and Accept/Reject semantics remain authoritative.

---

### Compatibility and Migration

- **CLI contract remains version 8.** No machine-readable response shapes,
  operation schemas, error codes, or CLI flags are modified or removed.
- **No capabilities removed.** Localized replacements (`localized-replacements-v1`),
  speculative apply (`speculative-search-apply-v1`), directional scoping
  (`--context-range`, `--around`), restore shortcuts (`restore-shortcuts-v1`),
  and space equivalence (`localized-space-equivalence-v1`) remain fully functional
  in the engine and CLI.
- **Narrowed baseline capability negotiation.** Standard agent skills and wrappers
  declare only the capabilities they actually use: `operations-stdin`,
  `agent-safety-profile-v2`, `recovery-envelope-v1`, and
  `localized-replacements-v1`. Speculative capabilities are opt-in for harnesses
  with explicit confidence policies.
- **Pre-1.0 integrations should remain release-pinned.** Skills, MCP servers, and
  custom harnesses should test and pin version `0.7.2` before adopting it.

### 1. Restoring the Extraction-First Golden Path

In v0.7.0 and v0.7.1, agents were asked to decide upfront among speculative
global apply, directionally scoped search windows, contextual extraction, and
restore shortcuts. In practice, this choice increased model reasoning tokens,
caused hesitation, and incurred multi-turn recovery loops whenever speculative
matching encountered repeated text (`AMBIGUOUS_TARGET`).

Version 0.7.2 re-establishes a single deterministic sequence across `AGENTS.md`,
`docs/AGENT_FAST_START.md`, and `docs/SKILL_AUTHORING.md`:

1. **Extract focused context** to inspect the target paragraph and draft changes:
   ```bash
   docx-redline extract contract.docx --search "termination" --around 3
   ```
2. **Apply once** using the inspected strong target (`paragraphId` plus `fingerprint`):
   ```bash
   node emit-operations.mjs | docx-redline apply contract.docx --operations - --profile agent --output reviewed.docx
   ```

Because strong targets bind to the batch-start source state, independent edits
require no manual sorting. Broad semantic edits use complete `modified` text;
small literal edits use localized `replacements`.

---

### 2. Localized Replacements as an Inspected Payload

Localized patching remains fully supported, but it is now decoupled from
speculative execution. Instead of guessing whether a literal phrase is globally
unique before inspecting the document, an agent inspects the target paragraph
first and then provides compact replacement instructions:

```json
{
  "type": "redline",
  "target": {
    "paragraphId": "1A2B3C4D",
    "fingerprint": "fnv1a32:9e2b0b70"
  },
  "replacements": [
    {
      "find": "thirty (30) days",
      "replace": "sixty (60) days"
    }
  ]
}
```

This retains the token-saving benefits of localized editing without risking
ambiguity refusal or uninspected document corruption:

- The agent transmits only the changed text, not the entire paragraph.
- In empirical benchmarks, this reduced generated edit request bytes by
  **60.6%** overall and by **90.8%** on long paragraphs (193 bytes vs 2,104
  bytes).
- The operation compiles against the inspected target paragraph before mutation
  and fails closed if the patch source is missing or ambiguous within that
  paragraph.

---

### 3. Single Computed Success Gate (`completion: true`)

Previous documentation directed agents to verify a multi-property predicate
checklist: `completion: true`, `written: true`, `results[i].change.committed: true`,
`finalDisposition: "applied"`, and
`change.verification.acceptedViewMatchesCompiledText: true`.

In v0.7.2, success evaluation is consolidated into the computed CLI signals:

- `completion: true`; and
- a non-null `outputPath`.

The CLI already aggregates atomic write status, mutation receipts, and compiled
accepted-view verification into `completion`. Exposing the internal checklist in
routine agent prompts added cognitive overhead without improving safety. Full
`change` evidence, bounded excerpts, and verification objects remain in stdout
for debugging and auditing.

---

### 4. Relocating Speculative Apply to Reference and Harness Policy

One-turn speculative apply (`apply --find ... --replace ...`), directional scoping
(`--context-range 1:3`, `--around 3`), and anchor uniqueness diagnostics
(`anchorMatchCount`) remain fully supported in the CLI and core engine.

They have been moved out of the primary launch cards and into
`docs/AGENT_KNOWLEDGE_BASE.md` and CLI `--help`. Speculative apply is best
suited for specialized harness automation with measured confidence thresholds,
rather than general-purpose agent prompts where deliberation costs exceed turn
savings.

---

### 5. Observed-State Restoration Branch

Restoration of deleted text is now structured as an observed-state branch rather
than an upfront choice:

1. If the user explicitly asks to restore deleted content, search `--view rejected`
   directly.
2. Otherwise, follow the actionable `selection.hint` if an accepted-view search
   identifies matches in rejected view.
3. Apply the restore against the inspected strong target, optionally using the
   concise `--restore --target-id <ID>` shortcut for verbatim restorations.

The restore shortcut restores only the inspected target; it does not infer
adjacent headings or companion paragraphs.

### Empirical Surface Evaluation

The controlled benchmark (`npm run benchmark:agent-surface`) replayed six
synthetic editing scenarios across three instruction policies against the same
underlying engine (7 measured iterations per scenario after warmup):

| Policy | Correct runs | Total calls | Calls/run | Failed calls | Edit request bytes | Median local ms |
|---|---:|---:|---:|---:|---:|---:|
| v0.6.2 extract/full | 42/42 | 84 | 2.00 | 0 | 27,034 | 3.86 |
| v0.7.1 speculation-led | 42/42 | 77 | 1.83 | 7 | 8,988 | 3.86 |
| v0.7.2 simplified extract/localized | 42/42 | 84 | 2.00 | 0 | 10,661 | 3.77 |

Key findings:

- **Zero failed calls:** The simplified policy achieved 100% first-attempt
  correctness across all scenarios, completely eliminating the 7 speculative
  failures caused by repeated text under v0.7.1.
- **60.6% payload reduction:** Compared to the v0.6.2 complete-paragraph
  baseline, generated edit request bytes dropped from 27,034 to 10,661 bytes.
- **Predictable 2-turn execution:** Every scenario completed in exactly 2 calls
  (1 extraction + 1 apply), removing turn variance and recovery overhead.
- **Local execution neutral:** Engine and I/O execution times remained identical
  (~3.8 ms), confirming that performance differences stem from agent turn and
  deliberation dynamics rather than engine runtime.

See [`docs/validation-reports/2026-09-14-agent-surface-simplification.md`](../validation-reports/2026-09-14-agent-surface-simplification.md)
for complete methodology and limitations.
