## @ansonlai/docx-redline-js v0.8.4

Version 0.8.4 fixes six defects reported by a downstream Word add-in. They cover edits to paragraphs with soft line
breaks, bullets generated into documents that already have lists, formatting a repeated phrase, and tables appended
after a paragraph. Tracked tables now use the markup Word itself writes for an inserted table. Before this release,
Word's Reject All left an empty table behind, and a table appended at the end of a document could hang Word. The
table-append results below were checked in real Microsoft Word. Word is only a test tool: the package still has no Word,
COM or Office dependency at runtime.

**Upgrade if you generate Markdown tables or lists, edit paragraphs that contain manual line breaks, or format text that
appears more than once in a paragraph.**

---

### Compatibility and Migration

- **CLI contract remains version 8.** One capability was added: `format-text-occurrence-v1`. No response shapes, flags
  or error codes were removed or changed.
- **Additive API and schema changes:**
  - `format` / `character-format` operations accept `textOccurrence` (integer, 1-based, default 1). This is in
    `docs/schemas/document-operations.schema.json` and `services/standalone-operation-runner.d.ts`.
  - `applyRedlineToOxml` honours `numberingXml` and `numberingIdState` options (declared on `RedlineOptions` in
    `index.d.ts`).
- **Behavior changes callers may notice:**
  - Generated tables are tracked row by row (`w:trPr/w:ins`, inserted cell runs and cell paragraph marks) instead of
    being wrapped in one `w:ins` around `w:tbl`. Code that looked for a `w:ins` around a `w:tbl` must look at the rows
    instead.
  - `rejectTrackedChangesInOoxml` removes a table once all of its rows are rejected, instead of leaving an empty
    `w:tbl`.
  - Appending a table after a paragraph (`modified: "<original>\n<table>"`) keeps the source paragraph untouched. It no
    longer tracks the paragraph as deleted and re-inserted.
  - Localized `replacements` whose `find` spans a soft line break are refused with `INVALID_OPERATION`. They were not
    reachable before, because every paragraph with a line break was refused.
  - When `numberingXml` is supplied without `numberingIdState`, `applyOperationsToDocumentXml` creates the state and
    stores it on the runtime context object you passed in. This lets later calls that share that object keep
    allocating new IDs.
  - A list request with explicit structured content (`explicitStructuredContent` / `structuredContent: true`) whose
    Markdown equals manually typed markers, such as `A. …` lines, is now a change, not a no-op. An implicit request
    still leaves an unchanged `1. Heading` alone.

### 1. Fixed: Soft-Break Text Could Not Become a List

A single paragraph whose items (`A. …`, `B. …`, `C. …`) were separated by manual line breaks (`<w:br/>`) could not be
turned into a list:

- `applyRedlineToOxml` refused it with `TARGET_NOT_FOUND`. Its target check read only `w:t` text, so Word's
  `Paragraph.text`, which reports the breaks, never matched.
- Requesting `A. …` lines as an explicit list was treated as a no-op, because the Markdown was byte-identical to the
  typed markers.

Changes in `engine/oxml-engine.js`:

- The target check now uses break-aware text spans (`buildTextSpansFromParagraphs`).
- An explicit structured request counts as a change unless the source is already an equivalent list.

`pipeline/serialization.js` now writes in-run `\n`, `\v` and `\t` as `<w:br/>` and `<w:tab/>` in both `w:t` and
`w:delText`. Before, Reject All restored the recitals as one run-on line.

---

### 2. Fixed: Localized Replacements Refused in Paragraphs With Line Breaks

`replacements` were refused with `INVALID_OPERATION` for any paragraph containing a manual line break, because the
accepted-view `exactText` shows the break as `"\n"`. There were three causes:

- The contract guard in `services/document-operation-contract.js`.
- `services/operation-batch-compiler.js` treated any target containing `"\n"` as dynamic. That skipped compiling the
  replacements, so the whole paragraph would have been deleted.
- The engine read lettered lines as a Markdown list and rebuilt them.

Now a `find` that lies within one line applies as a localized tracked change, and the breaks are preserved. Strong
(`paragraphId` / `fingerprint`) targets bind at batch start again. Compiled localized replacements are treated as
literal text unless `structuredContent: true` is explicit. A `find` or `replace` that spans or adds a line break is
refused.

---

### 3. Fixed: Generated Bullets Reused Existing Numbering IDs

Markdown bullets generated into a document that already defined `w:num 1` / `w:abstractNum 0` were given those same
IDs. After the numbering parts were merged, the existing definition won, so in Word the new "bullets" continued an
existing decimal list (5., 6., 7.).

The existing ID allocator only ran when the caller passed `numberingIdState`. The `openDocx` facade did this; the bare
runner and `applyRedlineToOxml` did not. Now:

- `applyOperationsToDocumentXml` creates the state from `numberingXml` (`services/batch-operation-orchestrator.js`).
- `applyRedlineToOxml` remaps generated numbering and the new paragraphs' `numId` references to new IDs when
  `numberingXml` or `numberingIdState` is supplied (`index.js`). Source and tracked-deleted paragraphs keep their IDs.

### 4. Added: `textOccurrence` for `format` Operations

A `format` operation could only format the first match of `textToFormat`. The in-paragraph occurrence was read from
`target.occurrence`, which paragraph targeting also uses to pick the N-th matching paragraph. So `occurrence: 2` on a
strongly targeted paragraph failed with `TARGET_NOT_FOUND`.

`textOccurrence` selects the match inside the resolved paragraph, independently of `target.occurrence`:

```json
{
  "type": "format",
  "target": { "paragraphId": "1A2B3C4D", "fingerprint": "…" },
  "textToFormat": "British Columbia",
  "textOccurrence": 2,
  "properties": { "bold": false }
}
```

- An out-of-range value fails with `PATCH_SOURCE_NOT_FOUND`. Zero, negative and non-integer values fail with
  `INVALID_OPERATION`.
- Calls without `textOccurrence` still read `target.occurrence` as before, for backward compatibility.

---

### 5. Fixed: Underline Lost When a Table Was Appended

Appending a Markdown table after a paragraph tracked the whole paragraph as deleted and re-inserted it as plain text.
Two cases lost the underline on Accept All:

- An underline added to that paragraph in an earlier same-author turn (`existingRevisions: 'merge-same-author'`).
- A new `++underline++` sent in the same replacement string as the table.

A paragraph followed by exactly one table now keeps the source paragraph in place, applies any inline format hints to
it, and inserts the table after it (`services/document-operation-mutations.js`, `deriveParagraphThenTableAppend` in
`services/operation-heuristics.js`). List items and paragraphs inside tables are excluded. When the table would end the
body, a trailing paragraph with a tracked-inserted mark follows it.

---

### 6. Fixed: Word's Reject All Left Tables and Paragraphs Behind

`generateTableOoxml` wrapped tracked tables in one `<w:ins>` around `<w:tbl>`. That is not valid WordprocessingML, and
it affected every generated table, including tables generated alongside list content
(`pipeline/list-generation.js`):

- Word saw only the cell text as inserted, so its Reject All left an empty table.
- A table appended at the end of a document could hang Word.
- The package's own `rejectTrackedChangesInOoxml` removed the table, so tests passed while Word disagreed.

`services/table-reconciliation.js` now writes Word's own inserted-table markup: `w:trPr/w:ins` on every row, cell runs
inside `w:ins`, and tracked-inserted cell paragraph marks.

Checked in Microsoft Word 16 for four cases: a table inserted mid-document, a table appended at the end, a table plus a
new underline, and a table appended after an earlier underline turn.

- **Reject All:** exactly the original seven paragraphs and no table.
- **Accept All:** the 3×3 table, plus one trailing empty paragraph for the end-of-document cases. The paragraph is
  underlined in both underline cases.

### Known Limitations

- Localized restore in the rejected view still refuses paragraphs that contain line breaks.
- The table-append path covers one paragraph followed by one table. A table before the paragraph, or several paragraphs
  plus a table, still tracks the source as deleted and re-inserted.
- Under `merge-same-author`, editing the text of a paragraph that carries your own pending formatting change still drops
  that formatting on Accept All.
- Separate `applyOperationsToDocumentXml` calls that each pass a fresh context object can allocate the same new
  numbering IDs, unless the numbering is merged between calls.
- Converting a plain paragraph to a list item and changing a list's format are still not canonical operations. These
  are tracked in [`docs/plans/2026-09-30-canonical-list-operations.md`](../plans/2026-09-30-canonical-list-operations.md).
