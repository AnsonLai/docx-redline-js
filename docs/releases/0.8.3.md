## @ansonlai/docx-redline-js v0.8.3

Version 0.8.3 fixes list edits whose tracked changes did not undo cleanly. Reject All left an extra empty paragraph after
an inserted paragraph, merged source paragraphs after a multi-paragraph list replacement, and restored deleted list
items with the wrong list type. Inspection also reported list, style and heading properties that a reviewer had already
changed as if they were current. The reports came from a downstream Word add-in, and each Reject All result below was
checked in real Microsoft Word. Word is only a test tool: the package still has no Word, COM or Office dependency at
runtime.

**Upgrade if you insert paragraphs, replace list ranges, or inspect documents that contain tracked paragraph-property
changes.** Nothing else changes.

---

### Compatibility and Migration

- **CLI contract remains version 8.** No response shapes, flags, error codes or capabilities were added, removed or
  changed.
- **No API or schema changes.** Operations, options and declarations are unchanged.
- **Behavior changes callers may notice:**
  - `numbering.xml` no longer gains unused definitions when a same-kind list range is replaced through `openDocx`.
  - The `numId` of an inserted list item can now equal the `numId` of the list it replaces, instead of a new one.
  - A multi-paragraph list replacement now emits one tracked-deleted paragraph per source paragraph, not one merged
    paragraph, so the markup is larger but rejects correctly.
  - Inspection no longer reports `list`, `styleId` or `headingLevel` from a `w:pPrChange` record.

---

### 1. Fixed: Reject All Leaves an Empty Paragraph After an Inserted Paragraph

Inserting a new paragraph after a plain paragraph, with `modified: "<original>\n<new>"`, tracked the new text but not the
new paragraph's mark. Reject All removed the text and left an empty paragraph behind. The inserted paragraph's mark is
now tracked as inserted (`services/document-operation-mutations.js`), so Reject All removes the paragraph entirely.

---

### 2. Fixed: Reject All Merges Source Paragraphs After a List Range Replacement

Replacing a multi-paragraph list range (`target` plus `targetEnd`) returned `ok` in 0.8.2, but the generated markup
collapsed every source paragraph into a single tracked-deleted paragraph. Reject All then merged them, for example into
`Bullet Root ABullet Insertion Anchor`. An empty paragraph in the middle of the range gave `AlphaGamma`, and a range made
only of empty paragraphs lost both of them.

`pipeline/list-generation.js` now keeps each source paragraph, including empty ones, as its own tracked-deleted
paragraph with its own tracked-deleted mark. Reject All restores every original paragraph boundary.

---

### 3. Fixed: Inspection Reports Historical Paragraph Properties as Current

A paragraph that carries a tracked paragraph-property change stores the old properties under `w:pPrChange`. Inspection
and list targeting searched all descendants of `w:pPr`, so they could read the old `numPr`, `pStyle` or `outlineLvl`.

- `list`, `styleId` and `headingLevel` in `services/document-inspection.js` now read only the paragraph's direct
  `w:pPr`.
- `getParagraphListInfo` in `core/list-targeting.js` does the same, so list targeting no longer treats a historical list
  binding as the paragraph's list.

---

### 4. Fixed: `openDocx` List Range Replacement Renumbered and Re-pointed Lists

Through the complete-document facade, a list range replacement changed more of the numbering than it was asked to:

- Deleted source paragraphs were remapped to a new generic `numId`, so Reject All restored them with the wrong list
  type.
- The new items started a separate list, so untouched items after the range restarted at 1.
- The edit added numbering definitions that nothing used.

Now deleted source paragraphs keep their `numPr`. When the replaced range uses one `numId` and the generated level
formats match it, the new items reuse that `numId`, continue the source list, and `numbering.xml` is unchanged
(`reuseSourceListNumbering` in `services/numbering-helpers.js`).

Limits of the reuse:

- It applies only when the range uses a single `numId` and every generated level format matches the source level
  format, with bullet, circle and square treated as the same kind.
- A format-changing edit, such as a numbered replacement of a bullet list, still allocates new definitions.
- Definitions created earlier in the same batch are not reused.

---

### 5. Fixed: Explicit List Start Values Were Lost

Generated list fragments are bare `<w:p>` elements with no `xmlns:w`. `orchestration/list-structural-fallback.js` failed
to parse them, so an explicit start such as `7. Header` lost its `startOverride`, and xmldom logged parse warnings.
Fragments are now parsed inside a namespaced wrapper. The generated numId is also taken from the first paragraph that
carries one, because tracked output starts with a deleted-original paragraph that has none.

---

### 6. Testing

- **New suites:** `tests/list_reject_fidelity_tests.mjs` models Word's Reject All semantics on a Word-authored nested
  list, including empty-middle and all-empty ranges. `tests/facade_list_numbering_tests.mjs` checks the `openDocx` list
  numbering behavior above. Both use `tests/fixtures/agentic-lists/nested-lists-source.docx`.
- **Extended suites:** `tests/document_inspection_edge_tests.mjs` covers `w:pPrChange`, and
  `tests/phase3_list_structural_fallback_tests.mjs` covers the start value and the absence of parse warnings.

---

### Known Limitations

[`docs/plans/2026-09-30-canonical-list-operations.md`](../plans/2026-09-30-canonical-list-operations.md) tracks what
this release does not cover:

- converting a plain paragraph to a list item is not yet supported as a canonical operation
- changing a list's format is not yet supported as a canonical operation
- `1. Header` to `1. Header` on a bare `document.xml` that is not a packaged `.docx` can fail with
  `RECEIPT_RECONCILIATION_FAILED`
