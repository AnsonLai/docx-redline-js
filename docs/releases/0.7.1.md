## @ansonlai/docx-redline-js v0.7.1

Version 0.7.1 is a focused agent-reliability patch. It removes misleading
revision diagnostics that could send an AI agent into repeated inspection
calls even though the underlying DOCX operation completed in milliseconds.

The engine remains OOXML-only and host-independent. This release adds no
runtime dependency and does not require Microsoft Word, Office automation,
COM, or a proprietary document API.

---

### Compatibility and Migration

- **CLI contract remains version 8.** The operation shapes and capabilities
  introduced in 0.7.0 are unchanged.
- **No behavior is removed.** The new compact extraction fields and
  `resolvedTarget.revisionView` are additive.
- **Pre-1.0 integrations should remain release-pinned.** Skills, MCP servers,
  and custom harnesses should test and pin version `0.7.1` before adopting it.

---

### 1. Self-Explanatory Revision Extraction

Compact `extract` output previously discarded revision metadata. With
`--revised`, a paragraph wholly deleted in the accepted view could therefore
look like an unexplained empty paragraph:

```json
{
  "revisionView": "accepted",
  "exactText": ""
}
```

Version 0.7.1 retains the compact cues needed to interpret that result:

```json
{
  "revisionView": "accepted",
  "exactText": "",
  "hasRevisions": true,
  "revisionAuthors": ["Reviewer A"],
  "deleted": true
}
```

In rejected view, a wholly inserted paragraph is similarly marked with
`inserted: true`. These indicators are emitted only when revision content is
genuinely hidden by the selected view; an ordinary empty paragraph is not
mislabelled.

This makes revision discovery actionable in one response. An agent no longer
needs to compare several accepted- and rejected-view ranges merely to determine
why a revised paragraph has empty `exactText`.

Example:

```bash
docx-redline extract contract.docx --range 52:62 --revised
```

### 2. Correct Rejected-View Restore Diagnostics

Restore targeting already resolved deleted paragraphs in rejected view, but
the resulting `resolvedTarget` receipt was rebuilt from accepted-view metadata.
For a wholly deleted paragraph, that could produce:

- the accepted-view fingerprint instead of the inspected rejected-view
  fingerprint;
- an empty diagnostic source string; and
- a spurious normalized mismatch against text that had actually matched
  exactly.

Resolution receipts now use the target descriptor's revision view consistently
for text, fingerprint generation, and target-match diagnostics. A restore made
from a rejected-view target therefore reports:

```json
{
  "resolvedTarget": {
    "revisionView": "rejected",
    "fingerprint": "fnv1a32:..."
  }
}
```

When the supplied rejected-view text is exact, the native result records
`targetTextMatch.mode: "exact"`; compact successful CLI output continues to
omit that redundant exact-match detail.

This changes diagnostic reporting only. Restore mutation, tracked-change
generation, validation, rollback, and source immutability are unchanged.

---

### 3. Alternate-View Hints Respect Active Filters

When a search returns no matches in the selected revision view, the CLI can
look in the alternate view and provide a `selection.hint`. That alternate scan
now honors the same canonical inspection options as the primary scan:

- `--revised` / `revisedOnly`;
- `--table` / `inTable: true`; and
- `--body` / `inTable: false`.

Previously, the hint path checked obsolete internal option names. A hint could
therefore count matches outside the requested table/body or revision scope.
The corrected count now describes the scope the caller actually requested.

---

### Agent Impact

This patch addresses a real-world slow path in which the engine took roughly
150 ms per command but an agent spent multiple full tool roundtrips trying to
explain blank revised paragraphs and contradictory restore diagnostics.

The intended workflow is again short:

1. Extract the relevant range in the appropriate revision view.
2. Read the returned revision cues directly.
3. Apply the restore or edit once using the inspected target.
4. Verify the normal completion, output, and receipt predicates.

The patch does not remove the reasoning needed to draft substantive text. It
removes avoidable discovery turns caused by ambiguous tool output.
