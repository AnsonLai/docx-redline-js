## @ansonlai/docx-redline-js v0.11.0

Version 0.11.0 is a small release with one addition and three fixes.

- **`mergeCommentParts`.** It merges a batch's comment output into comment parts held as XML strings, for hosts that keep
  package parts outside a ZIP (a Word add-in's Flat OPC package, a browser parts map).
- **Plain text stays plain everywhere.** A caller's `structuredContent: false` now also keeps inline Markdown literal in
  paragraphs a redline adds and in table cells.
- **One-column tables work.** A one-column Markdown separator (`| --- |`) is recognized, so a multi-line edit of a cell in
  a one-column table no longer inserts a stray `---` row or gets refused.
- **Safer comment merging.** A comment id repeated inside one incoming part is refused.

The CLI contract stays at version 9, with no new capabilities.

**Upgrade if you write comment parts back without `openDocx`, if you send `structuredContent: false` redlines that add
paragraphs or edit table cells, or if your documents have one-column tables.**

---

### Compatibility and Migration

- **CLI contract version 9 (unchanged).** No capability is added or removed.
- **Behavior changes callers may notice:**
  - **`structuredContent: false` reaches added paragraphs and table cells.** In 0.10.0 the plain-text contract covered
    only the rewritten target. Paragraphs added before or after it (`'Intro.\nUse __literal__ text'`) still had their
    inline Markdown turned into formatting and `#` lines turned into headings. Text written into table cells had its
    markers stripped. Both now stay literal. If you relied on `structuredContent: false` to format added paragraphs or
    cells, send `true` (the default).
  - **One-column tables are tables.** `| A |\n| --- |\n| B |` is now a valid one-column table: it reconciles, converts
    a paragraph to a table, and passes structured-content analysis. Before, it was refused `TABLE_SEPARATOR_REQUIRED`,
    or its separator became a data row. A bare `---` line, or `|---` without a closing pipe, is still not a separator.
  - **`ensureCommentsArtifactsInZip` (and so `openDocx`)**, when merging into an existing comments.xml, throws
    `DUPLICATE_COMMENT_ID` when the incoming part repeats an id. Before, both comments were written. With
    `replaceExisting`, or no existing part, it still writes the incoming part as is. An incoming part with no comments now leaves comments.xml
    byte-identical instead of re-serializing it.
- No defaults change.

### 1. `mergeCommentParts`

```javascript
import { mergeCommentParts } from '@ansonlai/docx-redline-js';

const merged = mergeCommentParts(
  { commentsXml, commentsExtendedXml, commentsIdsXml, commentsExtensibleXml }, // current parts, null when absent
  batchResult // e.g. an applyOperationsToDocumentXml result: commentsXml / commentsXmlMode,
              //      commentsExtendedXml / commentsExtendedXmlMode
);
if (merged.status === 'ok') {
  // write merged.parts; ensure relationships and content types for merged.changedParts
}
```

It merges exactly as `openDocx` does, through the same comments-merge helper and sibling reconciliation:

- **comments.xml:** appended (`'merge'`, the default) or replaced (`'replace'`).
- **commentsIds.xml and commentsExtensible.xml:** brought in line with comments.xml when the package has them. They
  are never created.
- **commentsExtended.xml:** replaced. A `'merge'` delta for parts that already have thread metadata is refused, because
  it can't be merged safely.

It returns `{ status, hasChanges, parts, changedParts, addedParts, error? }`. It's synchronous and never throws for
document content. On any error, `parts` is the input unchanged and `error.part` names the part:

| Code | When |
|---|---|
| `PARSE_ERROR` | A part, or an existing commentsIds/commentsExtensible part about to be reconciled, is not well-formed XML |
| `INVALID_COMMENT_PARTS` | An input is not a string, or a part has the wrong root element |
| `DUPLICATE_COMMENT_ID` | An incoming comment reuses an existing id, or another incoming comment's id (checked in every mode) |
| `UNSUPPORTED_EXISTING_COMMENT_THREAD_METADATA` | A `'merge'` commentsExtended delta for parts that already have commentsExtended.xml |

Relationships and content types stay with the host. `addedParts` lists the parts the input didn't have. It reflects
part presence only, so a host that owns relationships should ensure one for every part in `changedParts` (a package
can have comments.xml without its relationship).

Tests compare the result part for part with what `openDocx` writes, on a Word-authored threaded-comments package, for:

- a new comment, a reply and a resolve;
- a first comment on a package with no comment parts;
- a reply on a package with only comments.xml;
- sequential batches;
- a mixed batch: a text edit, a comment, a reply and a reopen.

### 2. Plain text in added paragraphs and table cells

A caller's `structuredContent: false` (per operation, or the batch option when the operation doesn't say) now keeps
every inline marker (`**`, `__`, `_`, `~~`, `++`) and `#` headings literal in:

- paragraphs a redline adds before, after or around its target, including several at once and a changed target;
- list siblings, which still join the target's list at its level (decimal, nested and bullet lists);
- `targetEnd` ranges, `replace`, untracked edits (`generateRedlines: false`) and `openDocx`;
- table cells, whether written by a caller's table Markdown or by a multi-line cell edit.

`structuredContent: true` still formats all of these. Reject All restores the source in every case.

### Fixed since 0.10.0

Reported by the Word add-in:

- **Inserted paragraphs lost literal markers.** `{ modified: 'Plain intro.\nUse __literal__ text', structuredContent:
  false }` gave Accept All `['Plain intro.', 'Use literal text']`. The plain-adjacency insertion route built each new
  paragraph without the caller's plain-text contract.

Found while testing this release:

- **One-column tables.** A multi-line redline of a cell in a one-column table (`'Cell text.\nSecond line'`) inserted a
  stray `---` row (`structuredContent: false`) or was refused `TABLE_SEPARATOR_REQUIRED` (`true`). The separator patterns
  in three places required two or more columns. This is also in 0.10.0 and earlier. A multi-line cell edit inserts the
  extra lines as rows below the target row; it does not add paragraphs inside the cell.
- **Duplicate comment ids within one incoming part** were written as is by `ensureCommentsArtifactsInZip` when merging
  into an existing comments.xml.
- The `applyCommentReplyToParts` declaration now includes `documentXml`.

### Upgrading from 0.10.0

1. Pin 0.11.0.
2. If you merge comment parts yourself (for example by wrapping parts in a ZIP to call `ensureCommentsArtifactsInZip`),
   switch to `mergeCommentParts`. Map its error codes, and ensure relationships for `changedParts`.
3. Audit call sites that send `structuredContent: false` with added paragraphs or table text and expect formatting.
