## @ansonlai/docx-redline-js v0.8.1

Version 0.8.1 fixes the Word "unreadable content" prompt on documents that already had comments, and brings the
package's comment threads in line with what Word writes. It also adds editing of existing headers and footers,
resolving and reopening comment threads, and deleting comments by id.

Every behavior in this release was checked against documents saved by Microsoft Word 16, and against our own
output opened in Word with repair disabled. Word is only a test tool: the package still has no Word, COM or Office
dependency at runtime.

**Upgrade if you redline documents that contain comments.** Earlier versions stamped a wrong content type onto
`word/commentsExtended.xml` on every save, and Word offered to repair the result.

---

### Compatibility and Migration

- **CLI contract remains version 8.** Every addition is additive: no response shapes, flags or error codes were
  removed or changed.
- **New CLI capabilities**, for wrappers that negotiate them:
  - `header-footer-parts-v1`: operations accept `part`.
  - `comment-resolve-operation-v1`: the `comment_resolve` operation.
  - `delete-comments-by-id-v1`: `delete-comments --comment-id`.
- **Operation schema additions:** an optional `part` on operations, and a new `comment_resolve` operation type
  (`docs/schemas/document-operations.schema.json`).
- **Headers and footers are opt-in.** An operation without `part` targets the body exactly as before, and body
  searches never match header or footer text.
- **Behavior changes callers may notice:**
  - `comment_reply` now adds the reply's own range and reference markers to `word/document.xml`. Word does not show a
    reply without them, so replies written by earlier versions did not appear in Word.
  - `deleteComments` and `resolveRevisions` now report `artifactsChanged` from a real comparison of the package,
    so the list can include `commentsIds.xml`, `commentsExtensible.xml`, `[Content_Types].xml` and header/footer parts.
  - `validateDocxPackage` rejects the old `application/vnd.ms-word.commentsExtended+xml` content type instead of
    accepting it.

### 1. Fixed: Word Asks to Repair Commented Documents

Word expects `word/commentsExtended.xml` to have the content type
`application/vnd.openxmlformats-officedocument.wordprocessingml.commentsExtended+xml`. Earlier versions wrote
`application/vnd.ms-word.commentsExtended+xml`. They also rewrote the part on every save of a document that already
had comments, even when the edit did not touch a comment. So any redline of a commented document made Word report
unreadable content.

- The content type is corrected. An edit that does not change comment threading now leaves every comment part, its
  content type and its relationship byte-identical.
- Files damaged by earlier versions are repaired on their next write. `repairKnownContentTypes(zip)` is exported for
  hosts that assemble packages themselves.
- The new part registry, `services/package-parts.js`, holds the path, content type and relationship type of every
  part the package reads or writes. Its entries are checked against Word-saved fixtures in `tests/fixtures/word-authored/`.
- `tests/package_content_type_contract_tests.mjs` runs on every OS, so this class of bug no longer depends on the
  Windows-only Word tests to be caught.

---

### 2. Comment Threads That Match Word

- **Threads keyed on the last paragraph.** Word joins `comments.xml` to `commentsExtended.xml` and `commentsIds.xml`
  through the `w14:paraId` of a comment's last paragraph. We used the first. Word's own multi-paragraph threads failed
  validation, and replies to them attached to the wrong key.
- **Replies are visible in Word.** Each reply now gets its own `commentRangeStart`, `commentRangeEnd` and
  `commentReference`, laid out next to the thread's own markers as Word writes them. A reply to a reply joins the root
  thread, because Word threads are flat. A parent with no anchor in the body fails with `PARENT_ANCHOR_NOT_FOUND`.
- **Replies to a resolved thread are resolved**, as Word writes them.
- **Edits no longer drop comment anchors.** An edit in the middle of a commented paragraph lost the trailing
  `commentRangeEnd` and reference run, leaving the comment unanchored.
- **Sibling parts are kept in step.** When a document has `commentsIds.xml` and `commentsExtensible.xml`, they gain or
  lose entries along with `comments.xml`. They are never created, since Word does not require them.

### 3. Resolve, Reopen and Delete Comments

Resolve or reopen the thread that contains a comment, as a batch operation or through the API:

```json
{ "type": "comment_resolve", "commentId": "8" }
{ "type": "comment_resolve", "commentId": "8", "resolved": false }
```

```javascript
await doc.resolveComment(8, { resolved: true });
```

- Resolved is a thread-level state in Word. Any id in the thread therefore updates the root and every reply together.
- Only `word/commentsExtended.xml` changes. Resolving a thread that is already resolved is `no_change`.
- Operations run in batch order, so `comment_reply` followed by `comment_resolve` closes the thread including the new
  reply.
- From the CLI, use `apply --operations`. There is no separate command.

Delete specific comments by id:

```javascript
await doc.deleteComments({ ids: [8] });
```

```bash
docx-redline delete-comments contract.docx --comment-id 8,9
```

Deleting a thread root also deletes its replies. An unknown id fails with `COMMENT_NOT_FOUND` for resolve and delete
alike, and nothing is written.

### 4. Header and Footer Editing

`inspect().headersFooters` lists the header and footer parts the document uses. For each one it gives:

- the path, kind and type (`default`, `first`, `even`)
- the sections it applies to, including sections that inherit it through Word's "link to previous"
- whether it is active, given `titlePg` and `evenAndOddHeaders`
- whether it contains fields
- its paragraph text

To edit a part, add `part` to an ordinary operation:

```json
{ "type": "replace", "part": { "kind": "footer", "type": "default", "section": 0 },
  "target": { "exactText": "Draft v1" }, "modified": "Draft v2" }
```

- **Selecting a part:** `part` is a selector `{ kind, type?, section? }` or a part path such as `word/footer2.xml`.
  `exactText` is the whole paragraph text, including the current result of any field.
- **Batches:** body and part operations can share one batch. Results keep their original indexes and carry `part` and
  `partSections`. Atomic batches roll back across the body and every part.
- **Revision ids** stay unique across the whole package. Receipts report the part and the final ids.
- **Accept and reject**, through the API and the CLI, also resolve tracked changes inside headers and footers.
- **Validation:** `validateDocxPackage` checks that every header and footer reference resolves to an existing,
  well-formed part with Word's content type.

These cases fail closed, and the whole request is refused before anything is written:

| Error code | When |
|---|---|
| `FIELD_EDIT_REFUSED` | An edit would change a field such as `PAGE` or `NUMPAGES`. Text around a field can be edited. |
| `COMMENT_IN_HEADER_FOOTER` | A comment, reply or resolve operation carries `part`. Word has no comments in headers or footers. |
| `PART_NOT_FOUND` / `PART_AMBIGUOUS` | The selector matches no part, or several. |

Creating a header or footer that does not exist is not supported. See `docs/plans/KNOWN_BUGS.md`, section 4.

### 5. Testing

- **Word-authored fixtures** in `tests/fixtures/word-authored/` cover threaded, resolved, multi-paragraph and
  reply-to-resolved comments, comment edge cases, and single- and multi-section headers and footers. The PowerShell
  scripts that generate them are in `scripts/`.
- **`npm run test:word:package`** (Windows with Word) generates 43 outputs through every write path and opens each one
  in Word with repair disabled. Through Word's object model it checks comment counts, thread parents, resolved state,
  and header/footer revisions and fields. A control file with the old content type must be refused by Word, which
  proves the check can detect the original bug.
- **New Node suites:** `package_content_type_contract_tests`, `package_parts_registry_tests`,
  `comment_thread_word_fixture_tests`, `comment_edge_case_fixture_tests`, `comment_marker_preservation_tests`,
  `comment_resolve_and_delete_tests`, `header_footer_tests` and `header_footer_edge_case_tests`.
- CI workflow fixes for the publish and test jobs.

---

### Known Limitations

`docs/plans/KNOWN_BUGS.md` sections 4 to 6 list what this release does not cover:

- creating or removing header and footer parts
- text boxes and images in headers and footers
- field protection for body edits
- empty comment-threading parts left in the package after the last comment is deleted
- `dateUtc` on entries added for Word-authored comments
- the lack of a repair-only save
