## @ansonlai/docx-redline-js v0.7.0

Version 0.7.0 targets the remaining latency in AI-driven document editing: tool
turns and generated paragraph text. It adds exact localized replacements,
fail-closed one-turn apply, directional provision scoping, and compact verified
change evidence while retaining the existing OOXML mutation pipeline.

The engine remains OOXML-only and host-independent. This release adds no runtime
dependency and does not require Microsoft Word, Office automation, COM, or a
proprietary document API. Existing reconciliation, tracked-change generation,
package validation, rollback, comment preservation, and Accept/Reject semantics
remain authoritative.

---

### Breaking Changes & Migration

- **CLI contract version 8:** Wrappers using the new fast path should require
  `localized-replacements-v1`, `speculative-search-apply-v1`, and
  `localized-change-summary-v1`. Negotiate only the capabilities actually used.
- **Pre-1.0 integration pinning:** Skills, MCP servers, and harnesses should pin
  the exact `0.7.0` package release they tested and declare contract 8 plus their
  minimum capability set. Treat another release or contract as unverified until
  compatibility tests pass.
- **No operation-shape removal:** Existing operations with complete `modified`
  content continue to work. Localized replacements and `change` results are
  additive; consumers ignoring unknown result fields remain compatible.

### 1. Localized Exact Replacements

A text operation can now provide exact replacement instructions instead of
reproducing the complete paragraph:

```json
{
  "type": "redline",
  "target": { "paragraphId": "1A2B3C4D" },
  "replacements": [
    {
      "find": "thirty (30) days",
      "replace": "sixty (60) days"
    }
  ]
}
```

The compiler resolves the source paragraph against the immutable batch-start
accepted view, applies non-overlapping patches simultaneously, synthesizes the
complete desired text, and passes it through the ordinary reconciliation,
validation, receipt, and rollback pipeline.

V1 is deliberately narrow:

- one accepted-view paragraph;
- exact, case-sensitive source matching;
- optional positive, 1-based `occurrence` within that paragraph;
- an empty `replace` may delete a span;
- ambiguous, missing, no-op, overlapping, or conflicting patches fail before
  mutation; and
- captures, rejected-view mutation, created-content dependencies, and
  cross-paragraph patches remain outside localized-replacement v1.

### 2. One-Turn Speculative Apply

Globally unique literal edits no longer require preliminary extraction:

```bash
docx-redline apply contract.docx --find "thirty (30) days" --replace "sixty (60) days" --profile agent --output reviewed.docx
```

When global matching is too broad, use a longer, fairly unique nearby phrase and
a directional paragraph scope. Longer anchors generally have a higher chance of
being unique:

```bash
docx-redline apply contract.docx --search "distinctive nearby heading or phrase" --context-range 1:3 --find "thirty (30) days" --replace "sixty (60) days" --profile agent --output reviewed.docx
```

`1:3` means strictly the next three physical paragraphs, excluding the heading
and preceding paragraphs. Other supported forms include `0:0`, `0:3`,
`-3:-1`, and `-3:3`; offsets are inclusive, bounded to `-20..20`, and clamped at
document boundaries. `--around 3` is shorthand for `-3:3`.

Every matching search anchor contributes a window. The library unions and
deduplicates those windows, then requires exactly one eligible paragraph to
contain the exact `find` literal. A generic or repeated anchor can therefore
widen the scope until multiple paragraphs contain `find`, producing a safe
`AMBIGUOUS_TARGET` failure and an extra recovery turn. On success,
`results[i].change.context.anchorMatchCount > 1` means the anchor was repeated;
confirm the returned location and excerpts. It is a specificity signal, not an
automatic failure. `--occurrence` may disambiguate only inside the uniquely
selected paragraph; it never chooses between paragraphs.

### 3. Refusal Without Output Damage

Speculation remains conservative:

- no contextual anchor returns `TARGET_NOT_FOUND`;
- no exact patch source returns `PATCH_SOURCE_NOT_FOUND`;
- multiple eligible paragraphs return `AMBIGUOUS_TARGET`;
- multiple source spans within one paragraph return
  `AMBIGUOUS_PATCH_SOURCE`; and
- invalid ranges and mixed targeting forms return a request error.

These failures include machine recovery metadata and bounded candidates. They
occur before output writing, so an existing destination is not truncated or
overwritten. The source remains immutable unless `--in-place` is explicit.

### 4. Explicit Post-Mutation Change Evidence

Successful localized operations return a compact evidence object inside the
corresponding operation result:

```json
{
  "status": "ok",
  "written": true,
  "completion": true,
  "results": [
    {
      "index": 1,
      "status": "applied",
      "change": {
        "kind": "localized_replacement",
        "committed": true,
        "finalDisposition": "applied",
        "target": {
          "paragraphId": "1A2B3C4D",
          "humanReference": "Relevant heading or text lead"
        },
        "context": {
          "search": "distinctive nearby heading or phrase",
          "range": "1:3",
          "anchorMatchCount": 1
        },
        "replacements": [
          {
            "find": "thirty (30) days",
            "replace": "sixty (60) days",
            "beforeExcerpt": "...thirty (30) days...",
            "afterExcerpt": "...sixty (60) days..."
          }
        ],
        "verification": {
          "acceptedViewMatchesCompiledText": true
        }
      }
    }
  ]
}
```

The excerpts come from the resolved batch-start source and compiled desired
text; the complete actual post-mutation accepted view is then compared with that
desired text. Positive verification therefore authenticates the reported after
state without returning the full paragraph. Excerpts are deterministically
bounded to 120 characters.

Report success only when `completion: true`, `written: true`, the output path is
non-null, every operation succeeded, and every localized result has
`change.committed: true`, `change.finalDisposition: "applied"`, and
`change.verification.acceptedViewMatchesCompiledText: true`. Atomic rollback
marks previously attempted evidence `committed: false` and `rolled_back`.

### 5. Agent Guidance and Development Wrapper

- Agent Fast Start, the repository launch card, Skill Authoring Contract,
  README, CLI help, and the advanced knowledge base now distinguish exact
  mechanical edits from semantic drafting.
- Literal names, dates, numbers, defined terms, and isolated phrase changes can
  use localized one-turn apply. Semantic requests such as “make this provision
  mutual” still begin with focused extraction and drafting.
- The skill-authoring contract warns pre-1.0 integrations to pin the exact
  package release and required CLI contract/capabilities.
- `examples/agent-session-wrapper.mjs` remains a development-only illustration,
  not a package export or alternate mutation engine.

### Performance Results

The controlled `npm run benchmark:localized` comparison uses the same runtime
for both paths, with 3 warmups and 11 measured iterations per case:

- tool turns fell from 2 to 1 (**50% reduction**);
- generated request bytes fell **65.06%–79.39%**;
- the deterministic request-token proxy fell **64.77%–78.98%**; and
- median native engine/I/O time ranged from **0.58% slower to 5.41% faster**,
  confirming that the intended savings are primarily outside the OOXML engine.

The token proxy is `ceil(UTF-8 request bytes / 4)`, not a provider tokenizer or
billed-token measurement. Provider reasoning, streaming, network, and full
Claude/OpenCode wall time were not estimated. See the
[localized rollout audit](../validation-reports/2026-09-14-localized-patching-rollout.md).
